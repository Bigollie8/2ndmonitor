# Ratings Implementation Plan (spec D)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a signed-in user rate a marketplace bundle 1-5 stars, and show the average on its catalog card.

**Architecture:** The server gains a `ratings` table keyed `(bundle_id, user_id)` so a second vote replaces the first rather than stacking. Aggregates are served from a **separate unsigned endpoint**, not the signed index — ratings change constantly and folding them into the index would re-sign it on every vote, for data that carries no security weight. The app gains a sign-in panel (it is anonymous today) storing the session token in the **DPAPI secret store**, never localStorage.

**Scope decision already taken:** star ratings only, **no written reviews**. The user's ask was "the ability to rate it"; free-text reviews on a personally-run server create a moderation burden that was not asked for.

**Tech Stack:** axum + SQLite (server), Rust + Tauri 2, React 18 + TypeScript, `node:test` via `tsx --test`, `cargo test`.

## Global Constraints

- **The signed index is not touched.** Its `bundles` array is serialized once and that exact string is signed; the app verifies the raw substring. Adding mutable data there would force a re-sign per vote and risk breaking every client's verification. Ratings ride a separate endpoint.
- The session token is a credential. It goes in the **DPAPI secret store** via the existing `secret_set`/`secret_get` commands — never `localStorage`, which is world-readable to anything running in the webview.
- All marketplace traffic goes through the Rust client (`get_capped`), never `fetch` from the page. No new CSP origin.
- `BROKER_COMMANDS` stays `{}`. No new app command is reachable from a non-main webview — every command added here must be in `permissions/app-commands.toml`, and the ACL drift tests must stay green.
- One rating per user per bundle, enforced by a primary key, not by application logic.
- Baselines: **568 frontend, 76 app-cargo, 66 server**. Each task states its new total.
- **The marketplace's public HTTPS route is down** (`docs/deferred-findings.md` item 20). Verification runs against a **local** server instance (`cargo run` in `server/`), and the app's marketplace URL is overridden to point at it. Say so explicitly rather than claiming live verification.

### Task 1: Server — the ratings table and endpoints

**Files:** modify `server/src/db.rs`, `server/src/lib.rs`; create `server/src/ratings.rs`.

- [ ] **Step 1: Schema**

```sql
CREATE TABLE IF NOT EXISTS ratings (
    bundle_id TEXT NOT NULL,
    user_id   INTEGER NOT NULL,
    stars     INTEGER NOT NULL,
    rated_at  INTEGER NOT NULL,
    PRIMARY KEY (bundle_id, user_id)
);
```

Keyed on `(bundle_id, user_id)` so `INSERT OR REPLACE` makes re-rating idempotent — one vote per user per bundle enforced by the database, not by a check that can be raced.

Note `bundle_id` without a version: a rating is of the bundle, not of a specific release. Say so in a comment.

**The live server has 15 published bundles and real accounts.** `db.rs` uses `CREATE TABLE IF NOT EXISTS`, so this is additive and safe — but do not alter or recreate any existing table.

- [ ] **Step 2: `POST /ratings`**

Body `{ id, stars }`, `Authorization: Bearer <session token>`. Reuse whatever `auth.rs` already uses to resolve a session token to a user — do not write a second path. Validate `stars` is an integer 1-5; reject anything else with a specific message. Reject a rating for a bundle that does not exist or is not approved.

- [ ] **Step 3: `GET /ratings`**

Returns `{ "<bundle_id>": { "avg": 4.2, "count": 17 } }` for all approved bundles with at least one rating. **Unsigned and public** — browse data, like downloads.

Round `avg` to one decimal server-side so every client displays the same number.

- [ ] **Step 4: Tests**

Rating requires auth (401 without); stars outside 1-5 rejected; re-rating replaces rather than stacks (rate 5, rate 3, expect count 1 and avg 3); a rating for an unapproved bundle is rejected; the aggregate endpoint returns correct averages across multiple users.

Run: `cd server && cargo test`. Baseline 66.

- [ ] **Step 5: Commit**

```bash
git add server/src
git commit -m "feat(server): per-user bundle ratings with an unsigned aggregate endpoint"
```

### Task 2: App — sign-in

**Files:** create `app/src/state/marketplaceAuth.ts`; modify `app/src-tauri/src/marketplace.rs`, `app/src-tauri/src/lib.rs`, `app/src-tauri/permissions/app-commands.toml`, `app/src/components/settings.tsx`.

The app has **no login UI at all** today. This is the piece that makes ratings possible.

- [ ] **Step 1: Rust commands**

`marketplace_login(url, email, password) -> Result<String, String>` — POSTs to `/auth/login` through `get_capped`, returns the session token. `marketplace_logout()` clears it.

Store the token via the existing DPAPI secret store under a fixed key (e.g. `marketplace_session`). **Do not return it to the frontend** — the frontend needs to know *whether* it is signed in, not what the token is. Add a `marketplace_session_status()` returning a bool and, if cheap, the masked email.

Add every new command to `permissions/app-commands.toml`. The ACL drift tests assert the registered set and the allowlist agree in both directions — they will fail loudly if you miss one, which is the point.

- [ ] **Step 2: Settings pane**

A **Marketplace account** section in Settings: email, password, Sign in / Sign out, and the current state. Password field `type="password"`. On failure show the server's message rather than a generic one — a wrong password and an unreachable server are different problems.

- [ ] **Step 3: Tests**

Pure logic only (this repo has no React harness): the state machine of signed-out → signing-in → signed-in → error, as a tested reducer or helper.

Run: `cd app && npm test && npx tsc -b`, then `cd src-tauri && cargo test`.

- [ ] **Step 4: Commit**

```bash
git add app/src app/src-tauri
git commit -m "feat(marketplace): sign-in with the session token in the DPAPI store"
```

### Task 3: App — rate and display

**Files:** modify `app/src/state/catalog.ts`, `app/src/components/CatalogCard.tsx`, `app/src/components/ContentLibrary.tsx`; create `app/src/components/StarRating.tsx`; modify `app/src-tauri/src/marketplace.rs`.

- [ ] **Step 1: Fetch aggregates**

`marketplace_fetch_ratings(url)` through `get_capped`, cached like the index. A failure is **silent** — a missing rating is not worth an error surface, exactly like a missing preview.

- [ ] **Step 2: Carry ratings on `CatalogItem`**

Add `rating: { avg: number; count: number } | null`. Populate it in `mergeCatalog` from a new input, defaulting to `null` — same shape as `downloads`. Update the existing fixtures.

- [ ] **Step 3: The widget**

`StarRating` renders the average and count, and — **only when signed in** — accepts a click to rate. Signed out, it displays but does not accept input, with a tooltip saying sign-in is required. Rating posts via a new `marketplace_rate(url, id, stars)` command and optimistically updates.

Put the display rule in a **pure tested function** — what to show for `null` ratings, zero count, and signed-out state — rather than in JSX conditionals. That is the pattern this project has used seven times now.

- [ ] **Step 4: Tests**

The display rule, and the merge carrying ratings through all four passes including pass 4's removed-item path.

Run: `cd app && npm test && npx tsc -b`.

- [ ] **Step 5: Commit**

```bash
git add app/src app/src-tauri
git commit -m "feat(catalog): star ratings on cards, gated on sign-in"
```

### Task 4: Verify against a local server

The public marketplace is down, so this runs against a local instance. **Say that plainly in the report** — do not describe it as live verification.

- [ ] **Step 1:** `cd server && cargo run`. Register a test account via `/auth/register` (dev mode returns the verify token in the response). Publish or seed a couple of bundles so there is something to rate.
- [ ] **Step 2:** `cd app && npm run tauri build`, launch the release exe, and point its marketplace URL at the local server via the Settings → Marketplace pane.
- [ ] **Step 3:** Sign in through the Settings UI. Confirm the token is in the DPAPI store and **not** in localStorage — check both.
- [ ] **Step 4:** Rate a bundle. Confirm the average appears on its card, that re-rating replaces rather than stacks, and that the count is right.
- [ ] **Step 5:** Sign out. Confirm the widget still displays averages but no longer accepts input.
- [ ] **Step 6:** Point the app back at the real marketplace URL and confirm nothing breaks when the ratings endpoint is unreachable — the cards must still render, ratings simply absent.

## Self-Review

**Coverage:** schema and endpoints → Task 1; sign-in → Task 2; rate and display → Task 3; verification → Task 4.

**Out of scope:** written reviews (decided against); moderation; rating tiles versus visualizers differently; any change to the signed index.

**Known risk:** the app has never had auth, so Task 2 introduces a credential-handling path where none existed. The session token must never reach `localStorage` or the frontend — the whole reason the DPAPI store exists.
